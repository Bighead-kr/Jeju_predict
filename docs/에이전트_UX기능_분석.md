## 1. 타겟 사용자 분석

### 1-1. 1차 사용자 — 제주 계통 운영자 (가장 중요)

| 속성 | 내용 |
|---|---|
| 직무 | 제주 전력거래소 / 한전 제주지역본부 계통운영팀 |
| 핵심 니즈 | 발전량 급변 **사전 경보**, 신뢰도 높은 수치 예측, 빠른 판단 근거 |
| 사용 패턴 | 대시보드 상시 모니터링 → 이상 징후 클릭 → 원인 확인 |
| 기술 수준 | IT 비전문가. 도메인 전문가. 수치는 읽지만 AI 내부 로직은 모름 |
| 핵심 불편 | "왜 이 예측이 나왔는가"를 빠르게 알고 싶다. 긴 대화창 보기 싫다 |

### 1-2. 2차 사용자 — 에너지 연구원 / 분석가

| 속성 | 내용 |
|---|---|
| 직무 | 신재생에너지 연구기관, 한전 KDN, KEPCO 부설 연구소 |
| 핵심 니즈 | 기간별 패턴 비교, 과거 유사 사례 검색, 리포트 생성 |
| 사용 패턴 | 기간 선택 → 분석 쿼리 → 결과 Export |
| 기술 수준 | 데이터 분석 능숙. API 직접 호출도 가능 |
| 핵심 불편 | 반복 조회를 매번 수동으로 해야 한다. 결과를 저장/공유하기 어렵다 |

### 1-3. 3차 사용자 — 프로젝트 팀 / 발표 시연

| 속성 | 내용 |
|---|---|
| 직무 | 대학원 연구팀, 공모전 발표, 학술 시연 |
| 핵심 니즈 | 한눈에 보이는 대시보드, 에이전트 추론 과정 시각화 |
| 사용 패턴 | 발표 중 실시간 데모 |
| 기술 수준 | 개발자. 코드 구조와 AI 흐름을 이해함 |

## 2. 헤르메스 에이전트 기능별 우리 시스템 적합성 분석

헤르메스의 6대 기능을 우리 도메인에 대입하여 **채택 여부와 구체 형태**를 판단한다.

### 기능 #1 — 연결 (멀티플랫폼)
> "Telegram, Discord, Slack, WhatsApp, Signal, 이메일, CLI 등에서 하나의 에이전트"

| 항목 | 판단 |
|---|---|
| 채택 여부 | **부분 채택** |
| 근거 | 제주 계통 운영자는 이미 사내 시스템(HMI, SCADA)에 익숙하다. 범용 메신저 연동보다 **이메일/SMS 경보 알림** 1가지가 훨씬 현실적 |
| 구체 형태 | 트리거 발동 시 → 이메일 알림 발송 (운영자 지정 수신인). Slack 연동은 연구원 팀 용도로 옵션 |
| 범위 | **에이전트 담당** (`tool_notify` 확장) |

### 기능 #2 — 기억 (지속 메모리)
> "프로젝트를 학습하고 스킬을 자동 생성하며 문제 해결 방식을 잊지 않습니다"

| 항목 | 판단 |
|---|---|
| 채택 여부 | **채택 (필수)** |
| 근거 | 현재는 대화 10턴 단기 기억만 존재. 운영자가 "지난 태풍 때 패턴"을 물으면 답 못 함 |
| 구체 형태 | ① **단기** — 현재 대화 히스토리 (현행 유지) ② **장기** — 과거 예측 결과 + 경보 이력 JSON 저장, FAISS 재활용 검색 ③ **이벤트 메모리** — 트리거 발동 시 이벤트를 날짜·원인·조치 결과와 함께 기록 |
| 범위 | **에이전트 담당** (P4 메모리 계층화, 에이전트_고도화_방안.md 참조) |

### 기능 #3 — 예약 (집중 자동화)
> "리포트, 백업, 브리핑을 자연어로 예약하고 게이트웨이를 통해 무인 실행"

| 항목 | 판단 |
|---|---|
| 채택 여부 | **채택 (운영자 1순위 니즈)** |
| 근거 | 계통 운영자는 매일 같은 시간(06시, 12시, 18시)에 발전량 브리핑이 필요하다. 지금은 매번 직접 질문해야 함 |
| 구체 형태 | APScheduler 기반 정시 예측 + 리포트 자동 생성. 설정 UI에서 예약 주기·수신인 지정 |
| 범위 | **에이전트 담당** (P5 능동 모니터링, P6 액션 도구) |

### 기능 #4 — 위임 (확장된 작업 / 하위 에이전트)
> "격리된 하위 에이전트가 각자의 대화, 터미널, Python RPC 스크립트를 갖고"

| 항목 | 판단 |
|---|---|
| 채택 여부 | **보류 (후순위)** |
| 근거 | 현재 도구 6개(predict, lookup, rag, kg, explain, compare)는 단일 에이전트로 충분히 처리 가능. 멀티에이전트는 P7(확장 단계)로 배치 |
| 구체 형태 | Phase 4 이후: 예측 에이전트 / 검증 에이전트 / 설명 에이전트 분리 |
| 범위 | **에이전트 담당** (장기 로드맵) |

### 기능 #5 — 검색 (웹 탐색)
> "웹 검색, 브라우저 자동화, 시각 이해, 이미지 생성, 다중 모델 추론"

| 항목 | 판단 |
|---|---|
| 채택 여부 | **부분 채택 (특화 검색만)** |
| 근거 | 범용 웹 검색은 불필요. 그러나 **기상청 API**에서 최신 수치 예보를 자동 조회하는 기능은 핵심 가치 |
| 구체 형태 | 기상청 단기예보 API 연동 → 실시간 기상 입력 자동 갱신 (현재 랜덤 시뮬레이션 대체). 뉴스 검색은 미채택 |
| 범위 | **에이전트 담당** (데이터 입력 파이프라인 개선) |

### 기능 #6 — 격리 샌드박스
> "로컬, Docker, SSH, Singularity, Modal 다섯 가지 후단"

| 항목 | 판단 |
|---|---|
| 채택 여부 | **미채택** |
| 근거 | 우리 시스템은 LSTM 추론 + KG 쿼리가 전부. 임의 코드 실행이 필요한 시나리오 없음. 오버엔지니어링 |

## 3. 에이전트 파트 필수 기능 목록 (우선순위)

> 챗봇 UI/대화 로직은 제외. 에이전트 코어 기능만 정리.

### P0 — 지금 당장 필요 (현재 치명적 빈틈)

| 기능 | 이유 | 구현 위치 |
|---|---|---|
| **기상청 API 실시간 연동** | 현재 `_build_window()`가 랜덤 시뮬레이션. 실제 기상 데이터 없이는 예측 의미 없음 | `agent.py` 입력 파이프라인 |
| **LLM Function Calling 전환** | 정적 if/elif 분기 → 동적 도구 선택. 이것만으로 "에이전트화" 70% 달성 | `agentic_chat.py` (챗봇 담당과 협의 필요) |
| **물리 규칙 검증 도구 분리** | `agent.py` 하드코딩된 물리 제약을 독립 `tool_validate()`로 분리 → 재사용·확장 용이 | `agent.py` |

### P1 — 1~2주 내 (운영자 핵심 니즈)

| 기능 | 이유 | 구현 위치 |
|---|---|---|
| **능동 모니터링 스케줄러** | 사용자가 묻지 않아도 정시 예측 + 트리거 경보 자동 감지 | 신규 `services/monitor.py` |
| **경보 알림 발송** | 고풍속/기압급변 트리거 시 운영자에게 이메일 발송 | 신규 `services/notifier.py` |
| **이벤트 이력 저장** | 경보 발동 이력, 예측 결과, 실제값 비교를 JSON으로 영속화 | 신규 `services/event_store.py` |

### P2 — 2~3주 내 (신뢰성 향상)

| 기능 | 이유 | 구현 위치 |
|---|---|---|
| **Plan-Act-Observe 루프** | 단발성 파이프라인 → confidence Low 시 반복 개선 (현재 1회 고정) | `agentic_chat.py` |
| **장기 메모리 (이벤트 검색)** | 과거 경보 이력을 FAISS로 검색 → "지난번 태풍 때" 질문 대응 | `services/memory.py` |
| **일간 운영 리포트 생성** | 24시간 예측 요약 + 경보 이력을 PDF/HTML로 자동 생성 | `services/report_gen.py` |

### P3 — 이후 (발표·시연 강화)

| 기능 | 이유 | 구현 위치 |
|---|---|---|
| **에이전트 추론 로그 시각화** | 현재 `tool_trace`를 UI에서 step-by-step으로 보여줌 | `index.html` 에이전트 패널 |
| **불확실성 구간 차트** | `refined_report`의 range_low/high를 차트에 표시 | `index.html` |
| **MC Dropout 예측 구간** | 2회 앙상블 → MC Dropout으로 확률 예측 구간 산출 | `agent.py` |

## 4. UI/UX 개선 방향 (에이전트 파트)

> 현재 `index.html`은 편집 스타일 대시보드. 챗봇 영역은 그대로 두고, **에이전트 전용 패널**만 추가/개선.

### 4-1. 현재 UI의 문제점 (에이전트 관점)

- 예측 결과가 숫자만 표시됨. **"왜 이 예측이 나왔는가" 근거가 없음**
- 경보(warnings)가 리스트로만 나옴. **심각도 강조 없음**
- 트리거 발동 여부, RAG 검색 결과, KG 이벤트가 UI에 노출되지 않음
- 에이전트의 추론 과정(`tool_trace`)이 콘솔에만 찍힘

### 4-2. 추가해야 할 UI 컴포넌트 (에이전트 담당)

#### ① 에이전트 상태 배너
```
[ 🟢 정상 모니터링 중 ]  /  [ 🟡 트리거 감지됨 — 고풍속 18m/s 초과 ]  /  [ 🔴 경보 발동 ]
```
- 페이지 상단 고정. 현재 에이전트 상태를 한눈에 파악
- 경보 시 배너 색상 변경 + 클릭 시 상세 이유 표시

#### ② 예측 근거 패널 (신뢰도 카드)
```
┌─────────────────────────────────────┐
│ 태양광 45.2 MW   [High] ✅         │
│ 풍력  128.7 MW   [Medium] ⚠️       │
│                                     │
│ 주요 영향 변수:                     │
│  • 풍속 14.2m/s (기여도 High)      │
│  • 전운량 3 (맑음, 태양광 유리)    │
│                                     │
│ 유사 과거 사례: 2024-08-12 14:00   │
│  → 태양광 42MW, 풍력 131MW         │
└─────────────────────────────────────┘
```
- 단순 수치 카드 → 근거 포함 카드로 확장
- KG 이벤트 / RAG 유사 사례 인라인 표시

#### ③ 경보 히스토리 패널
```
최근 경보
2026-06-14 09:00  기압 급변 (3.2hPa/3h)  [조치: 재예측 완료]
2026-06-13 21:00  고풍속 경보 (19.1m/s)  [조치: 알림 발송]
```
- 에이전트가 자율적으로 감지한 이벤트 이력 표시
- 운영자가 "에이전트가 무엇을 하고 있는지" 파악

#### ④ 에이전트 추론 로그 (접이식)
```
[펼치기] 에이전트 추론 과정
  1. intent_classifier → ["predict", "explain"]
  2. tool_predict → solar:45.2MW, wind:128.7MW (confidence: Medium)
  3. tool_validate → 경고: 전운량 급변 감지
  4. tool_rag → 유사 사례 3건 검색
  5. tool_explain → 영향 변수 분석 완료
```
- 기본 접힌 상태. 발표/데모 시 펼쳐서 에이전트 동작 시연

#### ⑤ 예약 관리 패널 (P1 구현 후)
```
정시 예측 스케줄
  [✅] 매일 06:00  —  일출 전 태양광 예측 브리핑
  [✅] 매일 12:00  —  주간 피크 발전량 점검
  [  ] 매일 18:00  —  야간 풍력 예측  [설정]

수신 알림
  이메일: operator@kepco.co.kr  [수정]
```

### 4-3. UX 원칙 (타겟 사용자 기준)

| 원칙 | 이유 |
|---|---|
| **수치는 항상 단위와 함께** | 운영자는 MW 단위 감각이 있음. 맥락 없는 숫자 혼란 유발 |
| **경보 시 클릭 2번 이내로 원인 파악** | 실시간 운영 중 긴 대화창 스크롤은 불가 |
| **에이전트 자율 행동은 로그로 남김** | 에이전트가 "혼자 무언가 했다"는 사실을 운영자가 알아야 신뢰 형성 |
| **예측 불확실성은 시각적 구간으로** | "45MW" 보다 "42~48MW" 표현이 운영 계획에 더 유용 |
| **챗봇은 보조 도구** | 대부분의 정보는 대시보드에서 직접 확인. 챗봇은 심화 질의용 |

## 5. Claude API 키 사용자 직접 연결 — 타당성 검토

### 5-1. 현재 상황

Claude API는 `agentic_chat.py`의 `_claude_classify()` / `_claude_answer()`에서만 사용된다.  
`agent.py`(예측 파이프라인)는 Claude API 미사용, 순수 PyTorch/NumPy 처리.

→ **이 기능은 에이전트 파트보다 챗봇 파트의 결정 사항**이다.  
  에이전트 담당 입장에서 시스템 전체 관점으로 의견만 제시한다.

### 5-2. 채택 여부: **현 단계에서는 미채택 권장**

#### 채택 시 장점
- 각 기관(한전, 연구소 등)이 자체 API 예산으로 운영 가능
- API 사용량 추적·비용 분리 가능
- 오픈소스 배포 시 사용자 자급자족 가능

#### 채택 시 문제점

| 문제 | 설명 |
|---|---|
| **보안 위험** | API 키를 프론트엔드/브라우저에 노출하거나 로컬 파일에 저장하면 유출 위험 |
| **복잡도 증가** | 키 입력 UI, 유효성 검증, 암호화 저장, 세션 관리 추가 필요 |
| **챗봇 담당 범위** | API 키 연결은 `agentic_chat.py`에 영향. 챗봇 담당과 협의 없이 에이전트 파트만으로 결정 불가 |
| **현 단계 불필요** | 학술 시연/공모전 수준에서는 팀 공용 키로 충분 |

#### 언제 채택해야 하는가
- 실제 한전/에너지기관에 납품(Production 배포) 시
- 여러 기관이 동시에 독립적으로 사용하는 SaaS 형태로 확장 시
- 기관별 사용량 분리 과금이 필요한 시점

### 5-3. 현실적 대안 (지금 당장 적용 가능)

API 키 노출 없이 환경변수 기반 운영을 유지하되, **배포 편의성**만 개선:

```
# .env.example (레포에 포함, 실제 키 미포함)
ANTHROPIC_API_KEY=your_api_key_here

# RUN.md에 설정 가이드 추가
```

→ 팀원이나 시연 환경에서 `.env` 파일만 수정하면 됨.  
→ UI에 키 입력창 없이도 운영 가능.

### 6-1. 공통 레이아웃 현황

```
┌─────────────────────────────────────────────────────────────┐
│  JEJU  제주 신재생에너지 AI 관제 플랫폼   [캘린더][지도][운영자]  │ ← 상단 네비
└─────────────────────────────────────────────────────────────┘
│                                                             │
│   [지도 뷰]  /  [캘린더 뷰]  /  [운영자 대시보드]               │ ← 탭 전환 콘텐츠
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**공통 문제점:**
- 에이전트 상태(정상/경보/트리거)가 **어느 탭에도 없음**. 운영자가 지금 에이전트가 무엇을 하는지 모름
- 경보 이력이 세션 내 메모리에도 없고, UI에도 없음
- 차트 틱 색상(`#94a3b8`)이 light 테마 배경(`#fafafa`)과 대비 부족 — dark 테마 잔재
- 탭 전환 시 이전 탭 컨텍스트(선택 날짜, 선택 권역)가 유지되지 않음

### 6-2. 지도 탭 (현행 → 개선)

#### 현행 구조
```
┌──────────────────────────────────┬──────────────────────┐
│  Leaflet 지도                    │  선택 지역 상세 예보  │
│  (CartoDB Positron, 그레이스케일) │  ☀️ 태양광 - MW      │
│  4개 권역 펄스 마커               │  💨 풍력 - MW        │
│  [제주시] [서귀포시]              │  ⚡ 총 발전량 - MW   │
│  [한경/고산] [구좌/성산]          │  AI 분석 텍스트      │
│                                  │  ─────────────────  │
│                                  │  [AI 인라인 채팅창]  │
└──────────────────────────────────┴──────────────────────┘
```

#### 진단된 문제점

| 문제 | 코드 근거 |
|---|---|
| 권역 데이터가 `regionMockData` 하드코딩 | JS 내 `regionMockData` 상수, API 연동 없음 |
| 경보 발생 시 지도에 시각 변화 없음 | `updateMapState()`에 경보 강조 로직 없음 |
| 마커 4개만 존재, 실제 발전소 위치 미표시 | `regionCoords`에 권역 중심 좌표만 있음 |
| 에이전트 트리거 상태가 지도에 반영 안 됨 | `report.trigger_active`를 지도에 연결하는 코드 없음 |
| 오른쪽 패널 AI 분석이 목업 텍스트 | `map-info-ai`에 `regionMockData.ai` 직접 주입 |

#### 개선안

**① 에이전트 상태 오버레이 배너 (지도 위 고정)**
```

┌──────────────────────────────────────┐
│ 🟢 에이전트 정상 모니터링            │  ← 정상 상태
│ 🟡 트리거 감지 — 고풍속 18.5m/s    │  ← 트리거 상태
│ 🔴 경보 발동 — 기압 급변 3.2hPa/3h │  ← 경보 상태

클릭 시 경보 상세 팝업
```
- `report.trigger_active` / `report.warnings` 기반으로 동적 갱신
- 색상: 초록(High) / 노랑(Medium, 트리거) / 빨강(Low, 경보)

**② 경보 권역 강조**
- 트리거 발동 권역의 마커 → `pulse-marker-red`로 전환 + 크기 1.5배
- 마커 툴팁에 경보 내용 표시: `"고풍속 경보 (19.1 m/s)"`

**③ 실발전소 레이어 (선택 추가)**
- 제주 주요 풍력단지(한경, 성산, 표선) 위치에 소형 터빈 아이콘 추가
- 클릭 시 해당 단지의 예측 발전량 표시

**④ 오른쪽 패널 → 예측 근거 카드로 재설계**

### 6-3. 캘린더 탭 (현행 → 개선)

#### 현행 구조
```
┌──────────────────────────────────┬──────────────────────┐
│  월간 달력 (7열 그리드)           │  선택 날짜 예보 요약 │
│  날짜 셀마다:                    │  시간대별 선택 드롭   │
│   ☀️ 태양광 [높음/보통/낮음]     │  ☀️ 태양광 발전량    │
│   💨 풍력  [높음/보통/낮음]      │  💨 풍력 발전량      │
│  (day%3, day%5 기반 더미 로직)   │  AI 일별 분석        │
│                                  │  [AI 인라인 채팅창]  │
└──────────────────────────────────┴──────────────────────┘
```

#### 진단된 문제점

| 문제 | 코드 근거 |
|---|---|
| 달력 셀 등급이 더미 로직 | `day % 3 === 0`, `day % 5 === 0` — 실제 예측값 미반영 |
| 경보 발생 날짜 표시 없음 | 경보 이력 저장 구조 자체가 없음 |
| 예약 스케줄 기능 없음 | 캘린더가 조회 전용, 예약 설정 UI 없음 |
| 과거 실적 vs 예측 비교 없음 | `is_actual` 플래그 존재하나 달력 셀에 미반영 |
| 날짜 셀 높이 고정 (`h-20`) | 경보 뱃지 추가 시 공간 부족 |

#### 개선안

**① 달력 셀 — 실제 예측 기반 등급 + 경보 뱃지**
```
현재 달력 셀:          개선 후 달력 셀:
┌──────────┐           ┌─────────────┐
│ 14       │           │ 14  ⚠️경보  │  ← 경보 이력 뱃지
│ ☀️ 높음  │           │ ☀️ 42.1MW   │  ← 실제 예측 수치
│ 💨 보통  │           │ 💨 128.7MW  │
└──────────┘           └─────────────┘
```
- 달력 로드 시 당월 예측값을 배치 API 호출로 프리패치
- 경보 발동 이력(`event_store`)이 있는 날짜에 `⚠️` 뱃지

**② 월간 발전량 누적 바 (달력 상단)**
```
┌──────────────────────────────────────────────────────┐
│ 6월 누적  ████████████████░░░░░░  1,234 / 2,100 MW  │
│           58.8% 달성  (목표 대비)                    │
└──────────────────────────────────────────────────────┘
```

**③ 예약 스케줄 아이콘 (달력 셀 내)**
- 자동 브리핑이 예약된 날짜 셀에 `🕐` 아이콘 표시
- 클릭 시 예약 설정 팝업: 시간 / 이메일 수신인 / 반복 여부

**④ 오른쪽 패널 — 실측 vs 예측 비교**
```
선택 날짜: 2025-08-15  [실측 데이터 ✅]

  ☀️ 태양광   실측: 48.3 MW
  💨 풍력     실측: 135.2 MW

  vs 당시 예측값: 태양광 45.1 MW / 풍력 131.0 MW
  예측 오차: 태양광 +3.2MW (+6.6%) / 풍력 +4.2MW (+3.2%)
```
- `report.is_actual` 플래그를 활용해 실측/예측 자동 구분

#### 진단된 문제점

| 문제 | 코드 근거 |
|---|---|
| 에이전트 상태 배너 없음 | 운영자 탭 최상단에 상태 표시 없음 |
| 경보 히스토리 패널 없음 | KG 물리 법칙 알림이 현재 1건뿐, 이력 누적 없음 |
| 내일 발전량이 `Math.random()` | `tomorrowTotal = total * (0.95 + Math.random() * 0.2)` |
| 예측 설명 패널 수동 트리거 | "설명 생성" 버튼 클릭 필요, 관제 실행 시 자동 갱신 안 됨 |
| 차트에 불확실성 구간 없음 | `refined_report`의 range_low/high가 차트에 미반영 |
| 기상 인디케이터가 하드코딩 | `"18.5 m/s"`, `"22.5 °C"` — 실제 입력 데이터와 무관 |

#### 개선안

**① 에이전트 상태 배너 (운영자 탭 상단 고정)**

**② KPI 카드 재설계**

| 오늘 예상 발전량 (API 연동) | 유지. 태양광/풍력 분리 표시 유지 |
| 내일 예상 발전량 (`Math.random()`) | 기상청 API 기반 실제 예측으로 교체 |

## 7. UI 재구성 계획

> **판단 근거**: 3탭 구조(지도/캘린더/운영자) 자체는 타겟 사용자(운영자·연구원·발표)와 잘 맞으므로 유지한다.  
> 핵심 문제는 "에이전트가 살아있다는 느낌"이 없다는 것이다. 지금은 버튼 눌러야만 동작하는 조회 시스템처럼 보인다.  
> **목표**: 탭을 열자마자 에이전트 상태가 보이고, 데이터가 살아 움직이고, 경보가 자연스럽게 흐르는 구조로 바꾼다.

### 7-1. 전체 레이아웃 재구성 (Before → After)

#### Before (현재)
```
┌────────────────────────────────────────────────────────────────┐
│  JEJU  AI 관제 플랫폼     [캘린더] [지도] [운영자]             │
```

## 8. 전체 정보구조(IA) 재설계 — "골격을 바꿔야 하는가"

> 앞의 6·7장은 **기존 3탭 안에서의 개선**이었다. 이 장은 한 단계 위, **"캘린더/지도/운영자라는 골격 자체가 옳은가"**를 판단한다.

### 8-1. 결론 먼저 (내 판단)

**기존 3개 화면은 유지하되, "탭"이라는 동등한 분류를 버린다.**  
이유는 아래에서 근거를 들지만, 핵심은 이것이다:

> 현재 3탭은 **"무슨 위젯을 보느냐"**(지도냐 / 달력이냐 / 대시보드냐)로 나뉘어 있다.  
> 그런데 타겟 사용자(운영자)의 머릿속은 **"무슨 일을 하느냐"**로 나뉜다 — "지금 괜찮나? / 어디가 문제지? / 앞으로 어떻게 되지?"  
> **위젯 기준 분류를 작업(task) 기준 분류로 바꿔야 한다.**

### 8-2. 기존 골격의 3가지 구조적 문제

| # | 문제 | 근거 |
|---|---|---|
| 1 | **탭이 "역할"과 "뷰"를 뒤섞음** | `운영자`는 *사용자 유형* 이름인데 `지도`·`캘린더`는 *위젯* 이름이다. 같은 층위가 아니다. 실제 운영자는 지도도, 달력도, 대시보드도 다 쓴다 → 탭이 사용자를 나누지도, 작업을 나누지도 못함 |
| 2 | **1차 사용자의 핵심 화면이 기본값이 아님** | `switchTab('map')`로 **지도가 첫 화면**. 그러나 1차 사용자(운영자)의 첫 질문은 "지금 발전량·경보 상황이 어떤가"다. 그 답이 있는 운영자 대시보드는 **3번째 탭에 숨어 있음** |
| 3 | **에이전트가 탭 어딘가에 갇혀 있음** | 에이전트 상태·경보·추론은 본질적으로 *모든 화면을 가로지르는 정보*다. 그런데 탭 구조에서는 특정 탭에만 존재 → "지도 보는 중에 경보가 떠도 모른다". 게다가 챗봇 입력창이 지도·캘린더에 **각각 중복**(`map-chat`/`cal-chat`)되어 대화 맥락이 끊김 |

> 정리: 3탭은 **"같은 예측 데이터를 보는 3개의 렌즈"**인데, 동등한 메뉴처럼 배치되어 ① 우선순위가 뒤집히고 ② 에이전트라는 가로축이 사라졌다.

### 8-3. 재설계 원칙 (문서 1~5장 방향에서 도출)

| 원칙 | 출처 | UI 적용 |
|---|---|---|
| 운영자가 1순위, 첫 화면은 "지금 상황" | 1-1 (사용 패턴: 상시 모니터링→이상 클릭→원인) | **관제 홈을 기본 랜딩으로** |
| 에이전트는 "응답형→감시·선제형" | 2장, 3장 P5 | **에이전트를 탭이 아닌 상시 레이어로** |
| 경보는 클릭 2번 내 원인 파악 | 4-3 | **경보를 전역 어디서나 접근** |
| 3개 렌즈(지금/공간/시간)는 유효 | 6장 진단 | **렌즈 자체는 유지, 재명명·재배치만** |

**변경의 본질은 3가지뿐이다 (그래서 과하지 않다):**

1. **재루팅** — 첫 화면을 `지도` → `관제 홈`(현 운영자 대시보드)으로. 1차 사용자가 열자마자 "지금 상황"을 본다.
2. **에이전트 레일 신설** — 상태·경보 이력·추론 로그·예약을 **오른쪽 상시 레일**로 빼서 *모든 렌즈를 가로지르게* 함. 탭을 옮겨도 경보가 사라지지 않는다. 발표 시연에서도 "에이전트가 생각하는 과정"을 띄워둔 채 화면 전환 가능.
3. **재명명** — `운영자`(역할명) → `관제 홈`, `지도`→`권역 지도`, `캘린더`→`예보 달력`. 세 개가 모두 "뷰"라는 같은 층위로 정렬되고, 각 이름이 *작업*을 가리킨다.

### 8-5. 에이전트 레일이 핵심인 이유

지금 흩어진 것들을 **하나의 세로 레일**로 모은다:

| 현재 위치 | → 레일로 이동 | 효과 |
|---|---|---|
| (없음) 에이전트 상태 | 🟢 현재 상태 | "에이전트가 살아있다"는 첫 신호 |
| 운영자 탭에만 KG 알림 | 📋 경보 이력 (전역) | 어느 렌즈에서든 경보 확인 |
| 콘솔에만 찍히는 `tool_trace` | 🧠 추론 로그 | 발표·신뢰성의 핵심, 헤르메스 "위임" 시연 대체 |
| (없음) 예약 | 🕐 예약 브리핑 | 헤르메스 "예약" 기능의 UI 거점 |
| `map-chat`+`cal-chat` 중복 | 💬 챗봇 입력(통합) | 대화 맥락 1개로 통일 (※ 챗봇 담당 구현) |

> 이 레일이 바로 헤르메스의 **연결·기억·예약**을 우리 도메인에 맞게 흡수한 형태다. 별도 메신저 연동 없이, 한 화면 안에서 "에이전트와 하나의 기억을 공유"하는 경험을 만든다.

### 8-6. 검토했으나 채택하지 않은 대안

| 대안 | 채택 안 한 이유 |
|---|---|
| **사용자 역할별 탭** (운영자 모드 / 연구원 모드 / 발표 모드) | 같은 사람이 상황 따라 역할이 바뀜. 모드 전환 비용만 늘고 데이터는 동일 → 분리 이득 없음 |
| **단일 페이지 통합** (탭 제거, 한 화면에 전부) | 정보 과밀. 운영자의 "이상 클릭→드릴다운" 흐름이 깨짐. 3개 렌즈 분리는 유효 |
| **좌측 아이콘 내비 레일**(콘솔형) | 더 확장적이나 현 코드(상단 탭) 대비 변경량 큼. 렌즈가 3~4개뿐이라 상단 탭으로 충분 → KISS |
| **에이전트 전용 4번째 탭** | 에이전트를 또 하나의 탭에 가두는 것 → 2장 진단(갇힘 문제)을 반복. 레일이어야 *가로지름* |

### 8-7. 현재 → 신규 매핑 (구현 부담 최소화)

기존 코드 자산은 거의 그대로 재배치된다. 전면 재작성이 아니다.

| 현재 요소 | 신규 위치 |
|---|---|
| `view-operator` (KPI·차트·RAG) | **관제 홈** (기본 랜딩으로 승격) |
| `view-map` (Leaflet) | **권역 지도** (이름만 변경) |
| `view-calendar` | **예보 달력** (이름만 변경) |
| `explain-panel` (설명 에이전트) | 관제 홈 본문 + 일부 요약은 레일 🧠 |
| `op-events-container` (KG 알림) | **에이전트 레일 📋 경보 이력**으로 이동 |
| `map-chat`/`cal-chat` 입력창 | **레일 💬 챗봇 입력**으로 통합 (챗봇 담당) |
| `switchTab('map')` 초기화 | `switchTab('home')`로 변경 (한 줄) |

> 즉 **HTML 블록 재배치 + 우측 레일 컬럼 신설 + 기본 탭 변경**이 골격 작업의 전부. 7장의 탭 내부 개선은 이 골격 위에서 그대로 진행된다.

### 8-8. 골격 작업 순서

| 순서 | 작업 | 효과 |
|---|---|---|
| 1 | 레이아웃을 `본문 + 우측 레일` 2컬럼 셸로 전환 | 모든 후속 작업의 토대 |
| 2 | 에이전트 레일에 🟢상태 + 📋경보 이력 배치 | 에이전트 상시 가시화 |
| 3 | 기본 랜딩을 관제 홈으로 재루팅 + 탭 재명명 | 1차 사용자 동선 정렬 |
| 4 | 챗봇 입력창을 레일로 통합 (챗봇 담당 협의) | 중복 제거·맥락 통일 |
| 5 | 🧠추론 로그 / 🕐예약을 레일에 추가 | 발표·예약 기능 거점 |
